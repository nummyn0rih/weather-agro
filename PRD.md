# PRD: Система мониторинга погоды для агрохозяйства

## 1. Обзор проекта

### 1.1 Назначение

Веб-приложение для сбора, хранения, анализа и визуализации погодных данных по локациям выращивания и закупки овощных культур. Цель — принятие решений на основе данных: планирование агротехнических операций, анализ сезонов, прогноз рисков.

### 1.2 Контекст использования

- **Пользователь:** один (личное использование)
- **Локации:** 10–20 точек на территории России
- **Регионы:** юг России (выращивание: томаты, огурцы, патиссоны, перец), центральная часть (кабачки), регионы закупки (лук, морковь, картофель, капуста, свёкла)
- **Тип выращивания:** открытый грунт
- **Глубина истории:** не менее 10 лет
- **Деплой:** VPS (основной) с возможностью локального запуска

### 1.3 Ключевые цели

1. Автоматический сбор погодных данных с нескольких источников
2. Долгосрочное хранение исторических данных (10+ лет)
3. Удобный анализ: дашборд, графики, сравнения, аномалии
4. Уведомления о критических погодных явлениях
5. Журнал агрономических событий с привязкой к погоде
6. Подготовка инфраструктуры для будущей ML-модели прогноза урожая

## 2. Технологический стек

### 2.1 Backend

- **Язык:** Python 3.11+
- **Framework:** FastAPI
- **ORM:** SQLAlchemy 2.0 + Alembic (миграции)
- **Планировщик:** APScheduler (ежедневная дозагрузка данных, бэкапы)
- **Валидация:** Pydantic v2
- **HTTP-клиент:** httpx (async)
- **Аутентификация:** JWT (один пользователь)

### 2.2 База данных

- **PostgreSQL 16 + TimescaleDB** (расширение для time-series)
- Hypertables для погодных данных
- Continuous aggregates для агрегаций по неделям/месяцам/сезонам

### 2.3 Frontend

- **React 18 + TypeScript**
- **Vite** (сборка)
- **Tailwind CSS + shadcn/ui** (UI-компоненты)
- **Стилистика:**
  - **Дашборд** — Apple HIG (Human Interface Guidelines): крупные скруглённые карточки, мягкие тени, премиальная типографика (SF Pro / Inter), пастельные акценты
  - **Таблицы и журнал** — Notion-style: минимализм, чёткая типографика, нейтральные цвета, плотная компоновка данных
- **Графики:** Recharts (основное) + Plotly (для сложных кейсов: heatmap, корреляции)
- **State management:** Zustand + TanStack Query (server state)
- **Routing:** React Router v6
- **Темы:** светлая/тёмная
- **Mobile-friendly:** адаптивная вёрстка

### 2.4 Telegram-бот

- **Библиотека:** python-telegram-bot (async)
- Запускается как отдельный сервис в Docker Compose

### 2.5 Инфраструктура

- **Docker + Docker Compose** (все сервисы)
- **Nginx** (reverse proxy, статика frontend)
- **Let's Encrypt** (HTTPS, certbot)
- **Бэкапы:** скрипт pg_dump → загрузка на Яндекс.Диск через WebDAV (ежедневно)

## 3. Источники данных

### 3.1 Используемые API

| Источник           | Роль        | Использование                                                       |
| ------------------ | ----------- | ------------------------------------------------------------------- |
| **Open-Meteo**     | Основной    | Исторические данные (с 1940 г.), прогноз до 16 дней, агро-параметры |
| **NASA POWER**     | Верификация | Исторические данные с 1981 г., кросс-валидация                      |
| **OpenWeatherMap** | Опционально | Текущая погода и краткосрочный прогноз                              |

Все источники — без оплаты. OWM требует API-ключ (бесплатный тариф).

### 3.2 Режим работы с источниками

Пользователь может выбрать в настройках для каждого параметра:

- Источник по умолчанию (Open-Meteo / NASA POWER / OpenWeatherMap)
- **Усреднённое значение** (среднее арифметическое доступных источников)
- Отдельные данные каждого источника (для сравнения)

В БД хранятся данные **от каждого источника отдельно**, усреднение вычисляется на лету.

## 4. Параметры погоды

### 4.1 Собираемые параметры (суточные агрегаты)

**Температурные:**

- Температура воздуха на 2м: мин / макс / средняя
- Температура почвы на глубинах: 0 см, 7 см, 28 см, 100 см (мин / макс / средняя)
- Точка росы (средняя)
- Количество часов с заморозками (T < 0°C)

**Влажность:**

- Относительная влажность воздуха (мин / макс / средняя)
- Влажность почвы на глубинах: 0–7 см, 7–28 см, 28–100 см (средняя)

**Осадки и испарение:**

- Осадки, мм (сумма)
- Эвапотранспирация ET0, мм (сумма)

**Солнечная радиация:**

- Солнечная радиация, МДж/м² (сумма)
- Часы солнечного света

**Ветер:**

- Скорость ветра на 10м, м/с (средняя, максимальная)

**Расчётные (вычисляются на стороне приложения):**

- **GDD** (Growing Degree Days) — с настраиваемой базовой температурой по культуре
- **VPD** (Vapor Pressure Deficit) — рассчитывается из T и RH

### 4.2 Прогнозные данные

- Прогноз на 16 дней вперёд (Open-Meteo)
- Хранится отдельно от исторических, обновляется ежедневно
- Можно сравнивать «прогноз vs факт» для оценки точности

## 5. Управление локациями

### 5.1 Атрибуты локации

- Название (например, «Поле №3, Краснодар»)
- Координаты: широта, долгота
- Регион / группа (например, «Юг», «Центр», «Закупка»)
- Тип: «Своё выращивание» / «Закупка»
- Список культур на локации
- Дата добавления
- Заметка

### 5.2 Действия

- Добавить / редактировать / удалить локацию
- При добавлении — автоматическая загрузка истории за 10+ лет (background task)
- Прогресс загрузки отображается в UI

## 6. Хранилище данных

### 6.1 Структура БД (основные таблицы)

```sql
-- Локации
locations (id, name, latitude, longitude, region, type, note, created_at)

-- Культуры (справочник)
crops (id, name, base_temperature, optimal_temp_min, optimal_temp_max)
-- base_temperature для расчёта GDD: томаты=10°C, огурцы=15°C, капуста=4°C и т.д.

-- Связь локация-культура
location_crops (location_id, crop_id, season_year)

-- Погодные данные (TimescaleDB hypertable)
weather_daily (
  time DATE,
  location_id INT,
  source VARCHAR, -- 'open_meteo' | 'nasa_power' | 'openweathermap'
  -- температурные
  temp_min, temp_max, temp_avg,
  soil_temp_0, soil_temp_7, soil_temp_28, soil_temp_100,
  dew_point,
  frost_hours,
  -- влажность
  humidity_min, humidity_max, humidity_avg,
  soil_moisture_0_7, soil_moisture_7_28, soil_moisture_28_100,
  -- осадки и испарение
  precipitation, et0,
  -- солнце
  solar_radiation, sunshine_hours,
  -- ветер
  wind_speed_avg, wind_speed_max,
  -- расчётные
  vpd, -- VPD считается при загрузке и сохраняется
  fetched_at TIMESTAMP
)
-- PRIMARY KEY (time, location_id, source)

-- Прогнозы
weather_forecast (time, location_id, source, ... те же поля, fetched_at)

-- Журнал агрономических событий
field_events (
  id, location_id, event_type, -- 'planting' | 'harvest' | 'note'
  event_date, crop_id,
  -- для planting
  variety, area_hectares,
  -- для harvest
  yield_kg, quality_rating,
  -- общее
  description TEXT,
  photos JSONB, -- массив URL
  created_at
)

-- Настройки алертов
alert_rules (
  id, name, parameter, condition, threshold,
  location_ids JSONB, -- [] = все локации
  enabled, telegram, created_at
)

-- История срабатываний алертов
alert_history (id, rule_id, location_id, triggered_at, value, message)

-- Пользователь (один)
users (id, username, password_hash, telegram_chat_id, created_at)

-- Настройки приложения
settings (key, value JSONB)
```

### 6.2 TimescaleDB политики

- `weather_daily` — hypertable с chunk_time_interval = 1 month
- Continuous aggregates: weekly, monthly, seasonal
- Compression policy: данные старше 1 года сжимаются

## 7. Функциональные требования

### 7.1 Дашборд (главная)

**Стилистика: Apple HIG**

Содержит:

- **Карточки локаций** (сетка) — текущая температура, осадки за сегодня, статус (норма/алерт), мини-график температуры за 7 дней
- **Активные алерты** — лента критических событий за последние 24 часа
- **Сводка по парку локаций** — средние/мин/макс показатели по всем точкам
- **Прогноз на 7 дней** — компактные карточки прогноза (выбранная локация)
- **Быстрые ссылки** — переход к графикам, журналу, отчётам

### 7.2 Раздел «Графики»

- Выбор локаций (одна или несколько)
- Выбор параметров (один или несколько)
- Выбор периода: пресеты (7д / 30д / сезон / год / всё время) + кастомный диапазон дат
- Выбор источника данных (или усреднение)
- Типы графиков:
  - **Временной ряд** (линейный)
  - **Сравнение локаций** на одном графике
  - **Сравнение «текущий сезон vs прошлые годы»** (overlay по годам)
  - **Heatmap** (например, температура по дням × годам)
  - **Накопительный график** (сумма осадков, GDD)
  - **Корреляции** между параметрами (scatter plot, матрица корреляций)
- Экспорт графика: PNG, SVG
- Экспорт данных: CSV, Excel

### 7.3 Раздел «Таблицы»

**Стилистика: Notion**

- Гибкая выборка по датам, локациям, параметрам
- Группировка: день / неделя / месяц / сезон / год
- Агрегации: мин / макс / среднее / сумма
- Сортировка, фильтрация, поиск
- Условное форматирование (цвет ячейки в зависимости от значения)
- Экспорт: CSV, Excel
- Сохранение пресетов выборок

### 7.4 Раздел «Аналитика»

- **Статистика за период** — сводная таблица с мин/макс/среднее/сумма по всем параметрам
- **Аномалии** — отклонения от климатической нормы (норма = среднее за 10 лет по этому дню/неделе/месяцу). Подсветка значений с отклонением >1σ, >2σ
- **Корреляции** — матрица корреляций Пирсона между параметрами с тепловой картой
- **Климатические нормы** — расчёт и визуализация многолетних норм по выбранной локации

### 7.5 Раздел «Журнал событий»

**Стилистика: Notion**

- Лента событий, сортировка по дате
- Фильтры: локация, тип события, культура, период
- Создание/редактирование/удаление событий
- Типы событий:
  - **Посадка/посев**: культура, сорт, площадь (га), дата
  - **Сбор урожая**: культура, объём (кг), оценка качества (1–5), дата
  - **Произвольная заметка**: текст + фото (до 5 фото)
- Привязка к погоде: при просмотре события — погодные условия в этот день
- Хранение фото — локально на VPS, в `/uploads/`

### 7.6 Раздел «Локации»

- Список локаций с поиском и фильтрами
- CRUD-операции
- При добавлении — выбор культур, запуск загрузки истории
- Статус загрузки данных (прогресс-бар)

### 7.7 Раздел «Алерты»

- **Правила алертов** — CRUD
  - Параметр (любой из собираемых)
  - Условие (>, <, =, between)
  - Пороговое значение
  - Локации (одна / группа / все)
  - Канал: Telegram (вкл/выкл)
- **История срабатываний** — лента с фильтрами

### 7.8 Раздел «Отчёты»

- Генерация PDF-отчёта за сезон по локации
- Содержание отчёта:
  - Общая статистика по погоде
  - Графики ключевых параметров
  - Аномалии и экстремумы
  - События из журнала
  - Урожайность (если есть данные)
- Экспорт: PDF
- **Библиотека:** WeasyPrint или ReportLab

### 7.9 Раздел «Настройки»

- Источники данных: приоритеты, режим усреднения
- API-ключи (OpenWeatherMap)
- Telegram: chat_id, токен бота
- Пороги алертов (быстрые шаблоны: «жара», «заморозки», «ливень»)
- Бэкапы: настройки Яндекс.Диска (логин, пароль приложения, путь)
- Управление культурами и базовыми температурами для GDD
- Профиль пользователя (смена пароля)

- `/start` — авторизация (привязка chat_id к пользователю по одноразовому коду)
- `/help` — справка
- `/locations` — список локаций
- `/weather <id_локации>` — текущая погода

- Push-сообщения при срабатывании алерта
- Формат: эмодзи + название локации + параметр + значение + время

### 8.3 Безопасность

- Бот работает только с привязанным chat_id
- Привязка через одноразовый код, генерируемый в UI

## 11. Аутентификация и безопасность

**Модель доступа:** small team (2–5 пользователей одной организации,
все доверенные). Регистрация только по инвайту от администратора.

**Роли:**

- `admin` — полный доступ, управление пользователями, настройки системы,
  справочники
- `user` — работа с данными (отчёты, журнал, дашборд),
  без доступа к настройкам и управлению пользователями

**Идентификатор пользователя:**

- Поле `username` (string), по соглашению содержит email-адрес
  пользователя
- Валидация формата email — на уровне Pydantic-схем при создании
  инвайта
- Уникальный, регистронезависимое сравнение при логине

**Аутентификация:**

- JWT-токены: access 15 мин, refresh 7 дней
- Хеширование паролей: bcrypt
- Rate limiting на эндпоинт логина (slowapi, защита от брутфорса)

**Регистрация:**

- Первый admin создаётся сидером из `ADMIN_USERNAME` / `ADMIN_PASSWORD`
  (значение `ADMIN_USERNAME` — email-строка)
- Последующие пользователи — только по инвайт-ссылке от admin
- Срок жизни инвайта: 7 дней
- Публичная регистрация отсутствует
- Email-уведомления отсутствуют (нет SMTP); admin передаёт
  инвайт-ссылку получателю любым каналом вручную

**Управление пользователями (admin only):**

- Создание и отзыв инвайтов
- Сброс пароля пользователя
- Деактивация пользователя (`is_active=False`) — блокирует логин,
  существующие токены инвалидируются при следующей проверке
- Список пользователей с их статусом

**Восстановление пароля:**

- Пользователь не может сбросить свой пароль самостоятельно
- Admin сбрасывает пароль другого пользователя через admin-эндпоинт
- Пароль admin восстанавливается пересозданием через сидер
  (admin останавливает контейнер, меняет `ADMIN_PASSWORD` в env,
  запускает сидер заново)

**Транспорт и секреты:**

- HTTPS обязателен в production (Let's Encrypt)
- CORS настроен только на домен фронтенда
- API-ключи и секреты — в `.env`, не в коде

## 13. План разработки (этапы)

### Этап 1: Фундамент (MVP-данные)

## 17. Принципы разработки задач

### 17.1 Разделение задач на слои

Каждая фича разбивается на 2–3 типа задач, выполняемых последовательно:

1. **Backend / Логика** — API, БД, расчёты, тесты. Проверяется через Swagger и unit-тесты.
2. **Frontend / Функциональный** — рабочий UI на базовых компонентах shadcn/ui без кастомного дизайна. Цель: убедиться, что всё работает end-to-end.
3. **Frontend / Визуальный** — применение дизайн-стилей (Apple HIG для дашборда, Notion для таблиц/журнала). Только CSS/стилевые правки, без изменения логики.

### 17.2 Когда не разбивать

- Мелкие фичи (< 50 строк суммарно)
- Сильно интерактивные элементы, где UX и логика неразделимы
- Прототипирование на ранних этапах

### 17.3 Definition of Done для каждого слоя

**Backend:**

- [ ] Эндпоинт работает в Swagger
- [ ] Покрыт хотя бы одним тестом (happy path)
- [ ] Pydantic-схемы описаны
- [ ] Миграция применяется без ошибок
- [ ] Логирование добавлено для критичных операций

**Frontend функциональный:**

- [ ] Все состояния обработаны (loading, error, empty, success)
- [ ] TypeScript без ошибок
- [ ] Работает на mobile (от 360px)
- [ ] Используются базовые shadcn/ui компоненты без кастомизации
- [ ] Запросы к API через TanStack Query

**Frontend визуальный:**

- [ ] Соответствует выбранному дизайн-стилю (Apple HIG / Notion)
- [ ] Светлая и тёмная темы
- [ ] Адаптивность сохранена
- [ ] Нет «дёрганий» layout при загрузке (skeleton loaders)
- [ ] Анимации/переходы плавные (если применимо)
- [ ] Логика не изменена (diff только в стилях)

### 17.4 Принципы формулирования задач для Claude Code

**Хорошая задача:**

- Имеет чёткие границы (один слой, одна фича)
- Содержит критерии готовности (DoD)
- Указывает зависимости (от каких задач)
- Содержит пример входных/выходных данных (для backend)
- Ссылается на референсы дизайна (для frontend визуального)

**Плохая задача:**

- «Сделай красиво» (нет конкретики)
- «Реализуй всё для графиков» (слишком широко)
- Смешивает логику и визуал в одной задаче
